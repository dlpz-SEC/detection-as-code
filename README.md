## Why This Exists

Most Detection-as-Code portfolio projects stop at basic file monitoring. This pipeline demonstrates real detection engineering maturity through structured validation, testing, and coverage analysis.

- **Rule Lifecycle Management**: Rules progress through `draft` → `experimental` → `production` → `deprecated` states
- **Behavioral Testing**: Rules are validated against curated log samples containing true positives AND benign activity
- **Confidence-Weighted Coverage**: MITRE heatmaps show detection confidence, not just "we have a rule"
- **False Positive Context**: Production rules include tuning metadata and exclusion patterns

## Rule Lifecycle States

| State | Description | Required by `validate_rules.py` |
|-------|-------------|---------------------------------|
| `draft` | Under development, not deployed | `title`, `logsource`, `detection`. Exempt from the CI MITRE-tag check |
| `experimental` | Testing in non-production | Draft fields + `description`, `tags`, `level`; at least one ATT&CK tag |
| `production` | Active in SIEM; exported to the ADTE manifest | Experimental fields + `status`, `author`, `date`, `id`; at least one technique tag |
| `deprecated` | Scheduled for removal | `title`, `logsource`, `detection`, `custom.deprecation_reason` |

Every lifecycle runs through the same lint, conversion and behavioral-test jobs. No lifecycle
requires test samples: a rule that no sample exercises still passes CI, and the coverage report
scores it as untested rather than passed.

Rules specify their state in the `custom.lifecycle` field:

```yaml
custom:
    lifecycle: production
    confidence: high
    false_positive_rate: low
    tuning_notes: |
        Exclude backup software (Veeam, Acronis) via process name
        Whitelist specific service accounts in finance dept
```

## Pipeline Stages

### 1. Schema Validation
`scripts/validate_rules.py --strict` runs hand-written checks: required fields per lifecycle,
`level` and `status` values, UUID format, ATT&CK tag format and tactic names, and unreferenced
selections. Under `--strict`, warnings fail the job too.

### 2. Unit Tests
Runs the pytest suite (`tests/`) against the pipeline tooling in `scripts/`, in parallel with
schema validation. A tooling regression fails the PR check, but conversion does not wait for it:
within a run, only the manifest export depends on the unit tests.

### 3. Linting
`scripts/sigma_lint.py` runs `sigma check --fail-on-issues`: pySigma's validators, including
ATT&CK tag validity, dangling conditions and detections, field names against the log source,
and duplicate IDs and titles. The ATT&CK release the tag validator checks against is pinned, so
a new MITRE release cannot change the verdict without a commit. A second check requires ATT&CK
tags on every non-draft rule and a technique ID on production and correlation rules.

### 4. SIEM Conversion
Converts rules to target SIEM query languages via a parallel matrix:
- Splunk SPL
- Microsoft Sentinel / Defender KQL (`kusto`)

### 5. Behavioral Testing
Two tiers of detection verification:
- **Tier 1 (offline, every push and PR that touches the pipeline paths):** converted queries are evaluated against test samples with an in-repo parser/AST — true positives detected (sensitivity), benign samples don't trigger (specificity). Hermetic, no infrastructure.
- **Tier 2 (functional, `workflow_dispatch`):** the same detections, authored as native Wazuh rules, are verified against a **live Wazuh engine** via the Manager API `logtest` endpoint — the real decoders and ruleset decide which rule fires. See [Functional Detection Testing](docs/wazuh_functional_testing.md).

### 6. Coverage Analysis
Generates a MITRE ATT&CK coverage report with confidence weighting (main branch only). Commits `docs/COVERAGE.md` and the ATT&CK Navigator layer back to the repo.

### 7. Rule Manifest Export
Exports every production rule to `docs/rule_manifest.json` for downstream consumption by ADTE (main branch only, gated on the unit tests). See [ADTE Integration](#adte-integration).

## Live Deployment

Converted queries are not the end of the pipeline — both target SIEMs have a real, tooled deploy
path, each with a rule-ID contract so nothing deploys silently or goes unaccounted for.

| Target | Seam | Deploy tool | Status |
|---|---|---|---|
| **Wazuh** | [`wazuh/`](wazuh/) — native XML + `rule_map.yml` | `scripts/deploy_wazuh_rules.py` (Manager API) | SSH brute-force twin verified against a **live engine** via `logtest` (Tier 2, last recorded run 2026-07-16). Windows twins cannot be verified that way |
| **Microsoft Sentinel** | [`sentinel/`](sentinel/) — `Sysmon.kql` parser + `rule_map.yml` | `scripts/deploy_sentinel_rules.py` (ARM REST) | Parser + 2 analytics rules deployed and **detection-validated on live telemetry** |

Both deployers are readback-verifying (`PUT` → `GET` → compare) and support `--dry-run` /
`--verify-only`. Every rule is dispositioned in `sentinel/rule_map.yml`; rules that cannot deploy
to Sentinel are skipped with a **logged reason**, never dropped silently. `wazuh/rule_map.yml`
maps the 4 rules that have a hand-ported Wazuh twin; the other 3 have none.

The Sentinel path exists because generated KQL does not run as-is: the Azure Monitor Agent lands
Sysmon in the generic `Event` table with fields buried in `EventData` XML, so a raw predicate
matches **zero rows with no error**. [`sentinel/parsers/Sysmon.kql`](sentinel/parsers/Sysmon.kql)
re-materialises those fields as columns; see [`sentinel/README.md`](sentinel/README.md) for the
full trap write-up and the live-verification evidence.

The lab those rules run in is itself code. [`infra/`](infra/) stands up the Log Analytics
workspace, the data collection rule, and an opt-in Windows Server 2022 event-source VM (AMA +
Sysmon) via Bicep. That VM can be promoted in-template to an **Active Directory domain
controller** (`promoteToDomainController`, Phase 2b): `promote-dc.ps1` installs AD DS and creates
the forest, `seed-ad.ps1` seeds OUs, users, groups, a Kerberoastable SPN and the audit
subcategories, and `fire-domain-logons.ps1` generates real authentication telemetry against it.
The DCR collects `4624/4625` on every associated host and, by default
(`collectDirectoryAuthEvents`), adds `4672/4728/4732/4768/4771/4776`; `4769` is deliberately
excluded on cost. The live fire authenticated over NTLM, so `4624/4625/4672/4776` were confirmed
in Sentinel and `4768/4771` were never produced. The build, the queries, and its honest limits
are in [`docs/AD_LAB_EVIDENCE.md`](docs/AD_LAB_EVIDENCE.md).

**The Azure lab is deliberately burst infrastructure: it is stood up, exercised, evidenced, and
torn down the same session, so it is not running now.** Cost model, per-phase deploy commands and
teardown are in [`infra/README.md`](infra/README.md). Re-running the pipeline against Sentinel
means redeploying it first.

## Quick Start

```bash
# Install dependencies
pip install -r scripts/requirements.txt
pip install -r scripts/requirements-sigma.txt

# Run the tooling unit tests
python -m pytest

# Lint rules the way CI does (pinned ATT&CK data, downloaded once)
python scripts/sigma_lint.py rules/

# Convert to Splunk SPL
sigma convert -t splunk --pipeline sysmon rules/windows/credential_access/lsass_memory_access.yml

# Generate coverage report (CI also passes --test-results from the behavioral tests;
# without it, every rule is scored as untested)
python scripts/generate_coverage.py --rules-dir rules --output docs/COVERAGE.md

# Export the production-rule manifest for ADTE
python scripts/export_manifest.py --rules-dir rules --output docs/rule_manifest.json
```

## ADTE Integration

This pipeline publishes a machine-readable manifest of production rules for [ADTE](https://github.com/dlpz-SEC) (Autonomous Detection Triage Engine), designed so triaged incidents can be mapped back to detection coverage, confidence weighting, and tuning guidance.

- **Artifact:** `docs/rule_manifest.json` — every `lifecycle: production` rule with its ATT&CK techniques, `confidence_weight`, false-positive rate, tuning notes, and `wazuh_rule_ids`.
- **Contract:** documented in [`docs/rule_manifest_schema.md`](docs/rule_manifest_schema.md). A consumer joins incidents to detections on the rule `id`, and joins **live Wazuh alerts** on `rule.id` ∈ `wazuh_rule_ids` — recovering the full detection context (confidence, tuning notes, techniques) for anything the Wazuh engine fires.
- **Status:** ADTE does not load the manifest yet. The schema is the contract for that join, not evidence that it runs.
- **Freshness:** regenerated on pushes to `main` that touch the pipeline paths; committed back only when rule content changes, so `generated_at` is a stable content-change watermark rather than a per-run timestamp.

The intended loop: **DaC defines detections → Wazuh and Sentinel run them → ADTE triages the
alerts with full rule context.** The first two arrows are proven. ADTE reads both SIEMs
(`--source wazuh`, `--source sentinel`), but triage of an alert raised by a rule from this repo,
and the join back to this manifest, have not been captured yet.

## Adding New Rules

1. Create rule in appropriate `rules/{os}/{tactic}/` directory
2. Follow naming convention: `{technique_name}_{variant}.yml`
3. Include all required fields (see `docs/RULE_STANDARD.md`)
4. Add test samples in `tests/samples/true_positives/`
5. Set `lifecycle: draft` initially
6. Open PR - CI will validate

## Coverage Metrics

`scripts/generate_coverage.py` scores each rule, then each technique.

**Rule score** = confidence weight × lifecycle weight × test-state weight

| Factor | Weights |
|--------|---------|
| Confidence (`custom.confidence`) | high 1.0, medium 0.6, low or missing 0.3 |
| Lifecycle (`custom.lifecycle`) | production 1.0, experimental 0.7, draft 0.2, deprecated 0 |
| Tier-1 test state | passed 1.0, untested 0.6, failed 0.5 |

A rule is **untested** when nothing exercised it: its query is an aggregation the Tier-1
evaluator cannot run (correlation rules), no true-positive sample routes to it, or it has no
Tier-1 result. It scores below a passing rule and above a failing one. False-positive rate is
not an input.

**Technique score** = the best rule's score, plus 0.1 × the sum of the others (bonus capped at
0.2), capped at 1.0. Bands: high ≥ 0.8, medium ≥ 0.5, low above 0. A technique with three
low-confidence rules still scores below one high-confidence rule.
